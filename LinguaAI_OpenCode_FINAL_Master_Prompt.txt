A. GLOBAL MASTER PROMPT FOR OPENCODE
Copy the following block into the first OpenCode session. The agent should save a short summary of it in docs/PROJECT_CONTEXT.md and treat this as the permanent product contract.
You are the lead full-stack engineer and product engineer for a project called LINGUAAI.

PRODUCT:
LinguaAI is a modern, responsive, AI-powered English-learning web application for secondary-school learners and independent learners. It combines a Duolingo-like guided path with a free-learning mode, a personal dictionary, vocabulary/grammar practice, reading, listening, speaking, writing, spelling, read-aloud, XP, streaks, daily challenges, progress analytics, and an AI teacher.

PRIMARY GOAL:
Build a real application from zero to a production-ready prototype. Do not build a static mockup. Routes, buttons, forms, data persistence, authentication, validation, empty states, loading states, error states, and core interactions must work.

TECH STACK:
- Next.js App Router
- TypeScript, strict mode
- Tailwind CSS
- shadcn/ui or equivalent accessible component primitives
- Supabase Auth, Postgres, Storage, Row Level Security
- Gemini API through a server-side provider adapter
- Use environment variables for secrets
- Use a typed validation layer such as Zod
- Use a practical testing setup appropriate to the repository
- Keep dependencies minimal

GEMINI:
Gemini is the main AI provider. The developer/user will provide the API key and model identifiers.
Create one provider abstraction so provider details are isolated:
lib/ai/provider.ts
lib/ai/gemini.ts
lib/ai/prompts/*
lib/ai/schemas/*
Never expose Gemini API keys to the browser.
Use Gemini for:
1. text generation / exercise generation
2. writing feedback and corrections
3. speaking feedback when supported by the chosen audio workflow
4. explanation and recommendation generation
5. TTS when configured and supported
6. optional content generation tools
Use structured JSON outputs validated with schemas whenever possible.
Provide graceful fallback/error messages when the API is unavailable.

CORE PRINCIPLES:
1. Build incrementally.
2. Never invent API keys, database credentials, model IDs, or production URLs.
3. Do not hard-code secrets.
4. Do not duplicate business logic across client components.
5. Prefer server-side actions/route handlers for privileged operations.
6. Keep UI responsive on mobile, tablet and desktop.
7. Make accessibility a first-class requirement.
8. Every feature must have loading, error, empty and success states.
9. Do not create dead buttons.

11. Avoid unnecessary packages.

13. Inspect only the files relevant to the current task.

16. If a requirement conflicts with the current architecture, preserve the product goal and choose the simplest maintainable solution.
17. Never silently remove an existing working feature to implement a new one.
18. Keep reusable data types in shared modules.
19. Use realistic seed/demo content, but clearly separate seed content from user-generated content.

H. SMART PATH AND RECOMMENDATION LOGIC
Smart Path should be deterministic enough to test and explainable enough that a student understands why something was recommended.
H1. Input signals
CEFR level estimate
Skill accuracy
Recent activity
Recent mistakes
Due vocabulary
Vocabulary mastery
Time since last practice
User daily time target
Current topic progress
Optional user goal (General English, IELTS, school, travel, work)
H2. Priority score (prototype)
priority =
  0.30 * weakness
+ 0.25 * recent_error_frequency
+ 0.20 * review_due
+ 0.10 * recency_gap
+ 0.10 * goal_relevance
+ 0.05 * variety_bonus

Apply caps so one skill does not consume the whole plan.
Then select a daily mix.
The exact weights are configuration, not scientific truth. They should be tuneable and tested experimentally.
H3. Daily plan example
Block	Target	Reason
Vocabulary	8 due/weak words	Review overdue vocabulary
Grammar	Past Simple vs Present Perfect	Repeated error pattern
Listening	1 short dialogue	Listening is currently weakest skill
Speaking	1 topic response	Apply target grammar/vocabulary
Spelling	5 words	Three words were repeatedly misspelled

H4. Recommendation examples
“Review Present Perfect” — triggered by repeated grammar errors.
“Practice these 8 words” — triggered by due reviews.
“Try a short listening exercise” — triggered by low recent listening accuracy.
“Use the word sustainable in a sentence” — triggered by recognition without productive use.
I. SPACED REVIEW AND VOCABULARY MASTERY
Use a simple, transparent review scheduler first. Do not implement a complex scientific spaced-repetition algorithm unless the product actually needs it.
Mastery	Suggested state
0	New
1	Learning
2	Familiar
3	Good
4	Strong
5	Mastered

Review interval can increase after correct answers and decrease after incorrect answers. Keep the scheduler configurable. Record only the signals needed to support review.
On correct:
  mastery += 1 up to max
  increase next_review interval

On incorrect:
  mastery -= 1 down to min
  shorten next_review interval

Also increase priority when:
  a word is repeatedly wrong
  a word is overdue
  the word is not used productively

M. PERFORMANCE AND TOKEN/CREDIT OPTIMIZATION
This section is specifically for using OpenCode efficiently and for reducing unnecessary Gemini/API usage.
M1. OpenCode token optimization
Fresh session per phase.
Persistent docs prevent the agent from re-reading the whole specification.
At session start, read only PROJECT_CONTEXT + DEVELOPMENT_STATUS.
Use rg/ripgrep to find symbols before opening files.
Inspect max ~3–8 relevant files at a time.
Do not dump full directories.
Do not read generated files.
Do not ask the agent to explain code that it already wrote unless debugging requires it.
End every session with a 10–20 line handoff summary.
Use one phase prompt at a time.
Commit after a stable phase if Git is used.
M2. Gemini/API cost optimization
Do not call AI for deterministic tasks; use local/database logic.
Do not call AI on every keypress.
Submit writing only on explicit Analyze button.
Submit speaking analysis once after recording or with explicit retry.
Generate lesson content offline/seed-time where possible.
Cache TTS audio by a stable content hash.
Cache repeated grammar explanations when content is identical.
Keep AI prompts short and structured.
Ask for concise JSON rather than long prose.
Set output token limits appropriate to each task.
Do not send the entire learner history; send a compact progress snapshot.
Use deterministic local scoring for MCQ, True/False, spelling where possible.
Batch small related recommendations into one AI request when appropriate.
M3. Performance optimization
Use server components for static/read-only content where practical.
Use client components only when interaction requires them.
Paginate long dictionary/history views.
Lazy-load audio-heavy or chart-heavy modules.

APPENDIX B — BUSINESS LOGIC RULES
A completed lesson must have an idempotent completion key or unique constraint to prevent double XP.
Saving a dictionary word must be idempotent per user + vocabulary item.
A Daily Challenge must be unique by user + local date.
AI feedback must reference the attempt it belongs to.
A retry after an AI timeout must not create duplicate writing/speaking attempts unless the user intentionally submits again.
Published content can be shared across users; learner-specific attempts cannot.
Deletion of a user should cascade or anonymize data according to the final privacy policy.
All scores shown on the UI should come from stored/derived data rather than hard-coded numbers.

Do not put Gemini API keys in NEXT_PUBLIC_* variables.
Do not store the entire chat/history/prompt context in every request.
Do not create giant React components for entire modules.
Do not use fake “database” arrays after Supabase is connected.
Do not silently swallow errors.
Do not report invented research data in the Daryn project.
Do not claim the application's informal scores are official CEFR/IELTS results.

====================================================================
19. AI UX RULES
====================================================================

AI is a product feature, not a decorative “AI” badge.

AI states must be explicit:
- generating;
- evaluating;
- available;
- unavailable;
- retrying.

Do not make the UI look frozen during AI calls.

Show concise progress language such as:
“Checking your writing…”
“Building feedback…”
“Preparing your next practice…”

Never expose raw API errors to learners.

Never show secret keys, server traces, internal prompts, or provider details.

====================================================================
20. AI RESPONSE COST CONTROL
====================================================================

Gemini should NOT be called for tasks that can be handled deterministically.

Use deterministic code for:
- navigation;
- XP calculations;
- streak calculations;
- score aggregation;
- due-date calculations;
- fixed multiple-choice checking;
- simple placement scoring;
- mastery state transitions.

Use Gemini only when language intelligence is actually valuable:
- writing feedback;
- speaking feedback;
- explanation generation;
- personalized natural-language recommendation;
- controlled exercise generation;
- optional content generation.

For predictable prompts:
- use short system instructions;
- send only relevant learner context;
- use structured output;
- cap output length;
- avoid sending the full history;
- summarize old history before passing it to AI;
- cache reusable content;
- debounce user-triggered AI actions;
- never evaluate every keystroke.

====================================================================
21. AI CONTEXT PACKING
====================================================================

Never send the entire database row set or entire learning history to Gemini.

Construct a compact context packet.

Recommended packet:
- user level;
- target skill;
- current topic;
- last 3–5 relevant mistakes;
- top 5–10 due vocabulary items;
- recent skill score;
- task text;
- learner answer.

Do not send irrelevant profile data.

Do not send the same instructions repeatedly if the provider adapter supports
reusable system instructions or equivalent mechanisms.

====================================================================
22. DETERMINISTIC FIRST, AI SECOND
====================================================================

This is a core architecture rule.

The system should use a two-layer recommendation model:

Layer 1 — Deterministic learning engine
- choose due vocabulary;
- detect weak skill;
- detect repeated topic mistakes;
- select eligible lessons;
- enforce prerequisite order;
- enforce daily time budget.

Layer 2 — AI explanation layer
- explain why the recommendation is useful;
- generate natural-language coaching;
- create optional extra practice.

Do not ask Gemini to decide everything.
This lowers latency, cost, unpredictability, and debugging complexity.

====================================================================
23. SAAS EMPTY / LOADING / ERROR / SUCCESS STATES
====================================================================

Every meaningful screen must have all relevant states.

Loading:
- use skeletons that resemble final layout;
- avoid flashing empty content;
- do not block the full app if only one card is loading.

Empty:
- explain why it is empty;
- tell the user what to do next;
- provide one CTA.

Error:
- human-readable message;
- retry action;
- no raw stack trace;
- preserve any safe local draft where possible.

Success:
- clear confirmation;
- next logical action;
- no excessive celebration for tiny tasks.

Partial failure:
If an AI card fails but the main lesson works, keep the lesson usable and show a
small retry state only for the failed AI card.

Focus management must be handled for modals, sheets, and route-level changes

33. SECURITY HARDENING
====================================================================

- content IDs;
- pagination;

====================================================================
34. PERFORMANCE BUDGET
====================================================================

Keep the app fast on average student devices.

Rules:
- lazy-load expensive learning modules;
- do not ship large audio/model assets on every page;
- cache static content;
- fetch only what the current screen needs;
- paginate long lists;
- avoid unnecessary rerenders;
- keep client components small;
- use server components where appropriate;
- memoize only when useful;
- avoid state updates inside animation or audio loops unless necessary;
- do not run AI work automatically on page load unless the feature requires it.

Target fast perceived interaction even if some AI tasks take longer.

For AI latency, show immediate UI state and allow the user to continue other
work whenever possible.

====================================================================
35. AUDIO / GEMINI TTS COST CONTROL
====================================================================

For TTS:
- generate only when needed;
- cache by normalized text + voice/model configuration;
- reuse cached audio;
- avoid generating audio on list pages for every word;
- allow user-triggered playback;
- preload only the next likely item, not the entire lesson.

If TTS is unavailable, the rest of the learning task must still work.
